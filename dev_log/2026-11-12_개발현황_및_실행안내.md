## 1. 현재 무엇을 할 수 있는가

현재 프로젝트는 **웹 서비스의 회원가입·로그인 기능을 제공하는 독립 로그인 모듈**이다. 화면만 만들어진 상태가 아니라, 브라우저 화면과 서버 API, SQLite 데이터 저장, 로그인 세션 처리가 연결되어 있다.

사용자는 이름·이메일·비밀번호로 가입하고, 이메일·비밀번호로 로그인할 수 있다. 가입하면 자동 로그인되며, 같은 화면에 이름과 이메일 및 로그아웃 버튼이 표시된다. 로그인 뒤 별도의 대시보드로 이동하지 않는다.

**개발 단계 판단: 로그인 모듈의 기본 기능 구현 및 서버 자동 테스트 검증까지 완료된 상태. 전체 학사 서비스나 운영 배포가 완료된 상태로 볼 근거는 없다.** 이 판단은 현재 코드와 테스트 결과를 기준으로 하며, 공식 일정이나 요구사항 대비 완료율을 의미하지 않는다.

## 4. 실행 방법

### 4.1 준비 사항

- `package.json`의 요구 버전은 **Node.js 24.12.0 이상**이다.
- 이번 확인 환경은 Node.js `v24.12.0`, npm `11.6.2`였다.
- 외부 npm 패키지, 별도 DB 서버 및 별도 프런트엔드 빌드는 필요하지 않다. 기본 실행을 위해 `npm install`을 먼저 할 필요도 없다.

### 4.2 기본 실행

PowerShell에서 다음 명령을 실행한다.

```powershell
Set-Location -LiteralPath 'C:\Users\박민우\Documents\ChatGPT\2026 ENDPoinT Team 07'
npm start
```

서버를 실행한 터미널을 유지한 채 브라우저에서 아래 주소에 접속한다.

```text
http://localhost:3000/login.html
```

`http://localhost:3000/`으로 접속해도 로그인 화면으로 이동한다. HTML 파일을 직접 열거나 Live Server로 실행하면 인증 API가 함께 제공되지 않으므로 위 방식으로 실행해야 한다.

기본 서버는 `127.0.0.1`에 연결되어 해당 PC에서 사용한다. 서버 종료는 실행 중인 터미널에서 `Ctrl+C`를 누른다.

### 4.3 화면에서 사용하는 순서

1. 로그인 화면의 **계정이 없나요? 회원가입** 버튼을 누른다.
2. 이름 1~50자, 이메일, 비밀번호 15~128자와 동일한 비밀번호 확인값을 입력한다.
3. 회원가입을 완료하면 같은 화면에 이름·이메일이 표시된다.
4. 새로고침하여 로그인 상태가 유지되는지 확인한다.
5. 로그아웃 버튼을 누른 후 가입한 이메일과 비밀번호로 다시 로그인한다.

기본 제공 계정이나 공통 비밀번호는 코드에 정의되어 있지 않다. 기존 DB의 계정 보유 여부는 이번 조사에서 확인하지 않았다.

### 4.4 개발 중 자동 재시작

```powershell
npm run dev
```

Node.js의 파일 변경 감시 기능으로 서버를 재시작한다. 개발 서버를 띄우기 전에 같은 포트에서 실행 중인 기존 서버를 종료한다.

### 4.5 설정을 바꾸는 방법

현재 폴더에서는 `.env.example`만 확인되었고 `.env`는 없었다. 기본값으로 실행할 때는 별도 설정이 필요 없다. 설정 변경이 필요할 때 예시를 복사한다.

```powershell
Copy-Item -LiteralPath '.env.example' -Destination '.env'
```

이미 `.env`를 만들어 사용 중이라면 복사로 덮어쓰지 말고 기존 파일을 수정한다.

| 항목 | 기본값 | 의미 |
| --- | --- | --- |
| `PORT` | `3000` | 서버 포트 |
| `HOST` | `127.0.0.1` | 서버가 연결을 받는 주소 |
| `APP_ORIGIN` | `http://localhost:3000` | 브라우저에서 사용하는 정확한 출처. 프로토콜·호스트·포트가 일치해야 함 |
| `NODE_ENV` | 예시 파일은 `development` | `production`이면 운영 쿠키 및 HTTPS 조건 적용 |
| `DB_PATH` | `storage/team07.db` | SQLite 저장 위치. 상대 경로는 실행 폴더 기준 |

예를 들어 포트를 3001로 변경한다면 `.env`에 `PORT=3001`, `APP_ORIGIN=http://localhost:3001`을 함께 설정하고 서버를 재시작한다. 브라우저도 `http://localhost:3001/login.html`로 접속한다. 기본 설정에서 `localhost` 대신 `127.0.0.1`을 브라우저 주소에 사용하면 출처가 달라 가입·로그인 요청이 거부될 수 있다.

## 5. 제공 API 및 향후 연결 지점

| 방식 | 주소 | 요청 / 결과 |
| --- | --- | --- |
| POST | `/api/auth/signup` | `{ name, email, password }` → 사용자 정보 및 로그인 쿠키 |
| POST | `/api/auth/login` | `{ email, password }` → 사용자 정보 및 로그인 쿠키 |
| GET | `/api/auth/me` | 로그인 사용자 정보. 로그인되지 않았거나 만료되면 401 |
| POST | `/api/auth/logout` | JSON 본문 `{}` → 현재 세션 폐기 |

POST API는 JSON 본문과 설정에 일치하는 `Origin`이 필요하다. 현재 화면의 `authRequest`가 브라우저 호출을 처리한다.

새 업무 화면에서 로그인 사용자를 확인하려면 `authRequest('me')`를 재사용할 수 있다. 개인 데이터용 API는 서버의 `currentUser(req)`로 사용자를 확인하고, 사용자 ID에 따라 데이터 접근을 제한하는 처리가 추가로 필요하다. 새 화면 파일은 `server/app.js`의 공개 파일 목록인 `staticFiles`에도 등록해야 한다.

- IP·계정별 요청 제한, 재시작 후 제한 유지, 제한 만료 및 로그인 성공 후 계정 제한 초기화

**검증 한계:** 이번 조사에서는 브라우저 화면을 직접 조작하는 수동 확인, 외부 네트워크 배포 확인, 부하 테스트 및 전체 보안 감사를 수행하지 않았다. 자동 테스트 통과만으로 실서비스 운영 준비가 모두 끝났다고 볼 수는 없다.

## 7. 운영 또는 전체 서비스 완성까지 남은 일

현재 코드에는 비밀번호 해시, 세션 토큰 해시 저장, HttpOnly·SameSite 쿠키, 출처 검사, 요청 제한, 공개 파일 제한 등의 보호 처리가 들어 있다. 이를 기반으로 서비스 목적에 맞게 다음 작업을 이어갈 수 있다.

1. **실제 업무 기능 개발:** 학점·성적·학적 정보 등 요구 업무의 화면, 데이터 테이블 및 API를 설계하고 연결한다.
2. **계정 운영 기능 보완:** 필요 범위에 따라 이메일 확인, 비밀번호 재설정, 프로필 수정, 탈퇴 및 관리자 기능을 구현한다.
3. **배포 환경 구성:** 운영 모드에서는 `NODE_ENV=production`, HTTPS 주소의 `APP_ORIGIN`, HTTPS 역방향 프록시가 필요하다. 현재 폴더에서는 배포 자동화나 배포 완료 근거를 확인하지 못했다.
4. **운영 검증 및 데이터 관리:** 브라우저 사용 흐름, 목표 사용자 수에 대한 부하, DB 백업·복구 및 접근 권한을 확인한다. SQLite의 WAL 사용을 고려해 일관된 백업 방법을 정한다.
5. **확장 시 요청 제한 검토:** 프록시 뒤에서는 여러 사용자가 같은 요청 제한을 공유할 수 있다. 실제 프록시 환경의 사용자별 제한을 마련하고, 여러 서버로 확장할 경우 DB와 제한 저장소 구성을 별도로 설계한다.

| 증상 | 확인 및 조치 |

| `node:sqlite` 또는 실행 옵션 관련 오류 | `node --version`으로 프로젝트 요구 버전 충족 여부 확인 |
| `EADDRINUSE` | 같은 포트의 기존 서버 종료 또는 `PORT`와 `APP_ORIGIN`을 함께 변경 |
| 화면은 열리는데 가입·로그인이 출처 오류로 실패 | 브라우저 주소와 `APP_ORIGIN`의 프로토콜·호스트·포트 일치 여부 확인 |
| 요청이 너무 많다는 오류 | 기본 제한 시간은 최대 15분. 잠시 기다린 후 재시도 |
| 브라우저에서 서버에 연결할 수 없음 | `npm start` 터미널이 실행 중인지, 접속 주소와 포트가 맞는지 확인 |
| 로그인 완료 후 다른 업무 화면이 나타나지 않음 | 현재 구현은 같은 화면에 로그인 사용자 정보를 표시하는 단계임 |

실제 설정 파일과 DB에는 설정값 및 사용자 정보가 포함될 수 있으므로 소스 공유 시 함께 배포하지 않는다. 기존 계정 데이터를 유지하려면 `storage` 폴더를 임의로 삭제하지 않는다.

## 9. 졸업학점 계산·성적 입력 및 조회의 현재 구현 상태

**현재 폴더에는 졸업학점 계산, 성적 입력, 성적 조회 로직이 구현되어 있지 않다.** 따라서 지금 `npm start`로 실행해도 해당 기능을 사용할 수 없다. 아래 처리 흐름은 향후 구현을 위한 제안이며, 현재 프로그램이 수행하는 동작을 설명하는 것은 아니다.

확인 근거는 다음과 같다.

- `README.md`는 로그인 관련 코드만 구현했으며 학점·성적 등의 기능은 포함하지 않는다고 명시한다.
- `server/schema.sql`에는 계정·세션·인증 시도 제한용 테이블만 있고, 수강 과목·성적·졸업 기준을 저장하는 테이블은 없다.
- `server/app.js`에 구현된 API는 회원가입, 로그인, 현재 사용자 확인, 로그아웃이다. 성적 저장·조회 및 졸업학점 계산 API는 없다.
- `public/`에는 로그인 화면과 인증 처리 파일만 있다. 성적 입력 폼, 성적 목록 및 졸업학점 결과 화면은 없다.
- 현재 자동 테스트 5개는 인증 관련 테스트이며, 졸업학점 계산이나 성적 처리의 정확성을 검증하지 않는다.

### 9.1 성적 입력 로직 — 향후 구현안

예상 흐름은 **로그인 확인 → 과목 정보 입력 → 서버 검증 → 본인 계정에 저장 → 조회·계산 결과 갱신**이다.

1. 로그인한 사용자가 학년도, 학기, 과목 코드, 과목명, 이수 구분, 학점, 성적 등급을 입력한다. 재수강 처리에 필요한 원수강 과목 정보도 별도로 연결할 수 있어야 한다.
2. 화면에서 필수 항목과 입력 형식을 확인한 뒤 저장 요청을 보낸다. 화면 검증 외에 서버에서도 같은 기준을 검증한다.
3. 서버는 기존 `currentUser(req)`로 로그인 사용자를 확인한다. 사용자 ID는 요청 본문에서 신뢰하지 않고 로그인 세션에서 가져온다.
4. 허용된 학기·이수 구분·성적 등급인지, 학점이 학교 정책에 맞는 값인지 확인한다. 같은 학기·과목의 중복 입력과 다른 학기의 재수강을 구분한다.
5. 성적을 해당 사용자의 수강 기록으로 저장한다. 수정·삭제도 기록 소유자가 본인인 경우에만 허용한다.
6. 저장 성공 후 목록과 졸업학점 집계를 다시 조회하여 화면에 반영한다. 저장 실패 시 성공으로 표시하지 않고 입력값과 오류를 안내한다.

현재는 위 입력값을 받을 화면, 저장용 테이블 및 API를 추가해야 하는 단계다. 학교별 등급 체계나 학점 범위는 아직 정해져 있지 않다.

### 9.2 성적 조회 로직 — 향후 구현안

예상 흐름은 **로그인 확인 → 본인 기록 조회 → 학기별 정렬·필터 → 과목 목록과 집계 표시**이다.

1. 서버가 세션으로 사용자를 확인하고 해당 사용자 ID에 속한 기록만 조회한다. 다른 사용자의 ID를 보내도 그 사람의 성적을 조회할 수 없어야 한다.
2. 학년도·학기·이수 구분 등의 선택 조건을 검증하고, 해당 조건에 맞는 과목을 정해진 순서로 반환한다.
3. 화면에 과목명, 이수 구분, 학점, 성적 및 재수강 상태를 표시한다. 기록이 없을 때는 빈 목록과 입력 안내를 제공한다.
4. 학기별 조회 결과와 전체 졸업학점 집계의 범위를 구분한다. 특정 학기 필터를 선택했다고 전체 졸업학점이 해당 학기 학점으로 바뀌지 않도록 한다.
5. 평균평점이 필요하면 학교의 등급별 환산값과 산입 대상 기준으로 별도 계산한다. 평균평점과 졸업 인정학점은 서로 다른 결과다.

평균평점의 일반적인 계산 구조는 아래와 같지만, 실제 산입 과목과 F·P/F·재수강 처리 기준은 적용할 학교 규정으로 확정해야 한다.

```text
평균평점 = Σ(평점 산입 과목의 학점 × 해당 등급의 환산평점)
           / Σ(평점 산입 과목의 학점)
```

분모가 0이면 평균평점을 산출할 수 없으므로 화면에는 ‘산출 대상 없음’으로 표시하는 처리가 필요하다.

### 9.3 졸업학점 계산 로직 — 향후 구현안

단순히 입력한 모든 과목의 학점을 더하는 방식으로는 졸업 요건 충족 여부를 판단하기 어렵다. **학생에게 적용되는 졸업 기준과 인정 가능한 이수 내역을 먼저 확정한 다음 영역별로 계산**해야 한다.

1. **적용 기준 선택:** 학교, 학과·전공, 입학 연도, 교육과정 및 복수전공 여부 등에 따라 적용할 졸업 기준을 찾는다. 기준이 없으면 ‘판정 불가’로 표시한다.
2. **성적 데이터 준비:** 로그인한 학생의 전체 수강 기록을 조회한다. 이수 완료·수강 중·미이수를 구분해 수강 중인 학점은 확정 취득학점에 합산하지 않는다.
3. **인정 과목 결정:** 합격 여부, 재수강, 동일·대체 과목, 편입·교류 학점 등의 정책을 적용하여 졸업학점으로 인정되는 과목과 인정 학점을 결정한다. 제외 사유도 결과에 남긴다.
4. **중복 처리:** 같은 과목의 반복 수강을 이중 합산하지 않으며, 한 과목의 여러 영역 인정 여부와 총학점 중복 합산 여부를 구분해 학교 기준대로 처리한다.
5. **영역별 집계:** 전공·교양 등 적용 교육과정의 영역별 인정학점을 계산한다. 전공필수·교양필수 같은 지정 과목 이수 여부도 별도로 확인한다.
6. **부족분 계산:** 총학점 및 각 영역별 최소 기준과 인정학점을 비교한다. 총학점이 충분해도 필수 과목이나 영역 기준이 부족하면 해당 조건은 미충족으로 표시한다.
7. **결과 제공:** 적용 기준, 인정 총학점, 영역별 인정학점·부족학점, 미이수 필수 과목, 제외 과목과 사유를 화면에 표시한다.

기본 계산 구조는 다음과 같다.

```text
인정 총학점 = 정책 적용 후 중복을 제거한 인정 과목의 학점 합계
총 부족학점 = max(0, 졸업 요구 총학점 - 인정 총학점)
영역별 부족학점 = max(0, 해당 영역의 요구학점 - 해당 영역의 인정학점)
학점·과목 요건 충족 = 총학점 기준 충족 AND 각 영역 기준 충족 AND 필수 과목 이수
```

예를 들어 가상의 기준이 총 130학점·전공 60학점·교양 30학점이고, 인정 결과가 총 124학점·전공 58학점·교양 32학점이면 총 부족분은 6학점, 전공 부족분은 2학점, 교양 부족분은 0학점이다. 전공 2학점을 추가 이수하면 총학점 부족분도 함께 줄어들 수 있으므로 부족분을 단순 합산해 8학점으로 안내해서는 안 된다. 이 숫자는 계산 설명용이며 실제 학교 기준이 아니다.

어학·논문·졸업시험·인증 등 학점 외 요건을 다루지 않는다면 결과 명칭은 ‘학점·과목 요건 충족 여부’로 제한해야 한다. 전체 졸업 가능 여부를 표시하려면 해당 요건까지 포함한 별도 검증이 필요하다.

### 9.4 구현에 필요한 데이터와 검증

| 추가할 요소 | 필요한 내용 |
| --- | --- |
| 학생 교육과정 정보 | 계정과 연결된 학과·전공·입학 연도·적용 교육과정 등 |
| 수강·성적 기록 | 소유 사용자 ID, 과목 식별자, 학년도·학기, 이수 구분, 학점, 등급, 이수 상태 및 재수강 관계 |
| 졸업 기준 | 총학점, 영역별 기준, 필수 과목, 학점 인정·중복·재수강 정책 및 기준 버전 |
| 입력·조회 화면 및 API | 본인 기록의 생성·조회·수정·삭제, 입력 검증, 접근 제한 및 오류 안내 |
| 계산 모듈과 결과 화면 | 기준 적용, 인정·제외 판정, 영역별 집계, 부족분 및 근거 표시 |
| 자동 테스트 | 다른 사용자 기록 접근 차단, 잘못된 입력, 중복 입력, F·P/F 처리, 재수강, 영역 중복, 기준 미설정, 빈 기록, 수정·삭제 후 재계산 |

학교·학과별 실제 졸업 기준과 성적 정책은 현재 폴더에 제공되어 있지 않다. 해당 기준을 확보한 뒤 구현해야 하며, 위 제안만으로 특정 학교의 졸업 판정이 가능하다고 볼 수는 없다.
